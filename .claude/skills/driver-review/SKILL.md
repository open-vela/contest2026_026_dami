# Contest 代码审查 Skill

对本项目的 C 源码进行轻量级代码质量审查，覆盖驱动和应用层代码。

## 触发格式

```
review <路径>
review <文件>
```

## 审查维度（7 维，100 分制）

| 维度 | 分值 | 审查要点 |
|------|:----:|----------|
| **内存安全** | 20 | 空指针解引用、缓冲区溢出、未初始化变量、内存泄漏 |
| **并发安全** | 15 | 竞态条件、锁使用不当、信号量/互斥量配对 |
| **资源管理** | 10 | fd/socket/timer 申请释放配对、错误路径资源泄漏 |
| **错误处理** | 10 | 返回值检查、错误传播、失败回滚 |
| **类型安全** | 10 | 整数溢出、类型截断、隐式转换风险 |
| **输入校验** | 15 | 用户输入边界检查、socket 数据校验、格式串安全 |
| **嵌入式专项** | 20 | 中断安全、DMA/cache、电源管理、硬件寄存器操作 |

## 严重度定义

| 严重度 | 扣分 | 定义 |
|--------|:----:|------|
| Critical | -15 | 导致 crash、数据损坏或安全漏洞 |
| High | -8 | 显著影响质量但不一定立即致命 |
| Medium | -3 | 值得修改但不阻塞 |
| Low | -1 | 改进建议 |

## 结论判定

| 总分 | 结论 |
|------|------|
| ≥ 80 且无 Critical | **PASS** |
| 60-79 或有可修复 Critical | **NEEDS_FIX** |
| < 60 | **REJECT** |

## 执行流程

### Step 1: 确定审查范围

按优先级检测 diff 范围：
1. 用户指定路径：`review <路径>`
2. 未提交改动：`git diff`
3. 已暂存改动：`git diff --cached`
4. 最近 commit：`git diff HEAD~1`

### Step 2: 读取源码

逐个读取变更的 `.c` / `.h` 文件，提取关键信息：
- 函数签名和调用关系
- 锁/信号量操作
- 内存分配释放
- 错误处理路径
- 硬件寄存器操作

### Step 3: 逐维度审查

按 7 个维度逐一检查，记录问题：

```markdown
### DR-001: [标题] [Critical/High/Medium/Low]
- **维度**：内存安全
- **文件**：app/camera_app/wifi_client.c:42
- **描述**：malloc 后未检查返回值
- **修复建议**：添加 NULL 检查
```

### Step 4: 输出报告

```markdown
## 代码审查报告

### 概览
- 文件数：X
- 代码行数：X
- 问题总数：X (Critical: X, High: X, Medium: X, Low: X)
- 总分：X/100
- 结论：PASS / NEEDS_FIX / REJECT

### 问题列表
（按严重度排序）

### 各维度得分
（维度分数表）
```

## 适用文件类型

- `*.c` / `*.h` — C 源码和头文件
- `Kconfig` / `Makefile` / `CMakeLists.txt` — 构建配置（仅检查明显错误）
- 跳过：`*.jsonl`、`*.md`、`*.xml`、`*.py`、`*.mp4`

## 注意事项

- **不修改代码**，仅给出审查报告和修复建议
- 审查范围聚焦本项目代码（`app/`、`board/`、`socket_proj/`）
- 对 NuttX 框架 API 使用方式参照 NuttX 编码规范
